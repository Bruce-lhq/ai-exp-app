# GPU-hosted mobile browser

Use this mode when the user needs to operate experiments from a phone independently of their computer. Read `docs/mobile-web.md` from the matching source checkout for packaging, runtime config, startup and tunnel instructions. The source GPU web bundle includes that document; current 0.4.1 binaries do not contain this feature.

Discover the hosting location first. Phone SSH authentication and local forwarding must work independently of the computer. Ask only for missing host, VPN, directory, interpreter or forwarding information; credentials stay in the SSH client, never chat or config. Do not re-test an already established phone chain unnecessarily.

1. Prepare frontend and source bundle locally. A bundle excludes private config and data; no SSH is needed for preparation. If the user asks for local work only, stop at local tests and artifacts. Never treat a tested mobile viewport as successful GPU deployment.
2. Inspect the existing agent path, Python and state directory when remote access is authorized. Reuse that exact state and queue. Never install a second scheduler or initialize fresh state to make the page work. Preserve the current agent and read-only marker.
3. The complete web backend needs a separate Python3.12+ environment; the existing standard-library agent and training environment may remain older. Verify the actual Ubuntu version and architecture. Do not copy a Mac virtualenv or assume the Ubuntu24.04 desktop executable runs on Ubuntu20.04. Prepare compatible runtime/dependencies separately if the GPU is offline.
4. Create a dedicated GPU workspace with `connection_mode=local`, absolute agent/Python/state paths and one matching host identifier. In this mode the backend executes the deployed agent locally; it must not SSH back into itself. Configuration/cache belongs to the GPU, and phone “local directory” browsing refers to GPU files. Mac metadata/cache remains separate.
5. Verify who owns port8765 before replacing a temporary web server; do not terminate unknown services. Keep the full backend listening only on127.0.0.1. Select a supervisor based on the actual host (systemd only if present); test detached survival and restart. Remote supervisor changes remain within the user's authorization.
6. Use iSH with OpenSSH as the default phone client; follow the generic commands in docs/mobile-web.md. Ask the user to establish their required network access separately; do not prescribe a vendor-specific VPN replacement or publish private network details. Configure SSH local forwarding from phone127.0.0.1:8765 to GPU127.0.0.1:8765. Use Safari and existing SSH client credentials. Do not open a public HTTP port or promise iOS tunnel/background longevity or notifications without evidence.
7. Verify read-only existing experiments, shared queue, history/cache/charts/table first. Use only an authorized isolated tiny run for start/pause/stop/queue/resume acceptance. Preserve strict-resume project validation. Never pause/adopt/delete a real ongoing run as a connectivity check.
8. Require actual iPhone evidence for Mac-off access, touch interactions, file saving, disconnection/reconnection and background-client behavior. Record simulated WebKit, real GPU and real phone results separately; report missing checks rather than marking the entire goal achieved.
